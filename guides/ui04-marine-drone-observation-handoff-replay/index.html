UI04 Marine Drone: A Replay Test for Observation Handoffs

Published 2026-11-07 by UNITED UAV Official

A reviewer receives a short clip from a waterfront exercise. A bright patch crosses the image, the controller display shows a map marker, and a message gives a time. The clip opens correctly, but the reviewer cannot tell which source produced the marker, when the camera frame was captured, or whether the clip is the original recording. Those gaps can survive a successful equipment demonstration. A procurement team evaluating the UI04 marine drone can expose them with an offline replay: give a second person only the proposed handoff package and ask that person to recover the observation, its source and the limits of what it supports.

Define the evidence the second team needs

The UI04 product listing describes a gimbal camera package, visible and thermal imaging with laser ranging, controller screen recording and local flight data. These are useful starting points for a quotation and a sample export. Ask the supplier which gimbal, controller and software versions the quotation covers, and which files that combination can actually produce. Confirm whether a screen recording and an original sensor recording are separately available, whether their timestamps have the same basis, and whether any range or position is saved as a field. The listing does not define those interfaces.

Write the acceptance question before asking for files. A practical question is whether an independent reviewer can locate the original view, identify when it was captured to the stated precision, and explain what any displayed position represents. Decide which parts of that answer are required for your organization and which may remain unknown. A supplier may provide enough data for a record of what appeared on the controller without providing enough data to reconstruct a target position. Those are different deliverables and should receive different acceptance decisions.

Keep the test focused on information quality. It can be run with staged media, synthetic events and approved sample files at a desk. It does not need to simulate an emergency or evaluate how an aircraft should be flown. The responsible organization retains its own response and operating procedures.

Give the observation an identity independent of the clip

Use an observation identifier that stays the same if an operator corrects a note or exports a smaller viewing copy. A workable record pairs a package namespace and observation identifier with a revision number. Record the observer role, source channel, attachment identifiers, capture time or interval, and a plain description of what appeared. Keep any interpretation in a separate field. A note such as bright shape near the edge of the frame describes the recorded view. An explanation of what caused the shape belongs in a later, separately attributed entry.

A visible image, a thermal view and a controller overlay can refer to the same observation. Preserve their source relationships before counting them. Two representations made by the same operator from the same moment are useful for comparison; they do not establish that two independent observations occurred. When two separate observations may depict the same feature, preserve both identifiers and add a possible relationship with the reviewer's reason. A later reviewer can then revisit the association without having to split a merged record.

Decide how a reviewer should find the source in practice. For video, a file identifier and a presentation time or frame identifier may be needed. For a still, an image identifier may be enough. If a file contains several channels, record which channel carries the observation. A filename alone is weak evidence: two exports from different devices can use the same default name, and a desktop tool may rename a file on import.

Separate capture time, playback time and receipt time

Ask what event each time field describes. An original frame may carry a capture time from one clock; a screen recording can have a playback offset from its own start; a coordinator's message can have a receipt time from another system. File creation time can describe copying or export. Keep the raw values with their source and role, then place any normalized value in a separate field. Use an explicit date and UTC offset when an absolute time is supported. When the source only provides elapsed playback time, preserve that value and state that absolute capture time is unavailable until a valid alignment exists.

A test export should include enough information to show how alignment was made. One common approach in a controlled recording is to identify a reference event in both streams and record the pairing. One reliable pair can establish an offset at that point. Two pairs can help estimate a relative rate difference over the interval they bracket, provided the clip has continuous timing and neither clock jumped. A third event held out of the fit is useful for checking whether the simple mapping describes the recording. Treat gaps, edits and restarts as separate segments when they break that assumption.

Test this with the actual player or parser proposed for review. Playback software can display a rounded offset or conceal a discontinuity when a clip has been trimmed. Ask the reviewer to locate a named source event without using the filename, file modification time or a screenshot of the original controller. Record which time was found directly and which was calculated.

Work a timing example with an uncertainty interval

In an invented clip, a marker at playback offset ten seconds corresponds to reference time 14:03:10.200 UTC. A second marker at seventy seconds corresponds to 14:04:10.260 UTC on the same date. The reference advances 60.060 seconds over 60.000 playback seconds. For a continuous interval between the markers, a linear mapping advances 1.001 reference seconds per playback second. An event at playback offset forty seconds is halfway between the markers, giving an estimated reference time of 14:03:40.230 UTC.

Suppose the declared maximum pairing error is 0.20 seconds at each anchor and the event can be placed within 0.04 playback seconds. Inside the anchor interval, linear interpolation is a weighted average, so the anchor contribution is bounded by 0.20 seconds under those assumptions. The event placement contributes about 0.040 seconds after rate conversion. With no additional uncertainty in this toy example, a conservative rounded bound is plus or minus 0.25 seconds. This is a fixture for testing a record format; the numbers say nothing about the UI04's recording or clock accuracy.

Now suppose a second event has estimated time 14:03:40.400 UTC with the same uncertainty. Its nominal time is later, but the possible intervals overlap. A reviewer cannot establish order from those timestamps alone. A trustworthy sequence field in the same source stream could provide a separate basis for ordering. A useful replay system reports the uncertainty or flags the ordering as unresolved instead of sorting the decimal values and presenting the result as fact.

Type the positions that travel with an observation

A position field should have a role. Typical roles include aircraft position at capture, observer or controller position, a point manually placed on a map, and an estimated position of the observed feature. Determine which roles the offered configuration exports. A controller screenshot can show a position that is useful for context without identifying the location of the feature in the camera image. Preserve the visible annotation and its source, and mark the role unknown if the interface does not document it.

If a value is supplied as coordinates, retain the coordinate reference system or datum, axis order, units, method and corresponding time. Record whether the value was copied, measured, inferred or manually entered. A range reading, when available, describes a distance under a measurement model. It does not by itself determine a point on a map. Ask the supplier which metadata accompanies any offered position output and whether it survives the exact export path used in the handoff. Keep the example fixture free of real incident locations.

Make unsupported fields visible in the receiving view. If the source has only aircraft position, the target position remains empty with an explanation. A zero coordinate, the last good point or a position from another record should never stand in for a missing value. A good test puts two different position roles in a single record and checks that a reviewer can distinguish them after export, import and display.

Keep original and derived files in the same chain

Build a manifest that lists each expected file and its role. At minimum, include a unique file identifier, relative path, media type, byte length and a content digest such as SHA-256. Add the source device or application, capture or export basis and the related observation identifiers where known. A receiving team can recalculate the digest to check whether the bytes match the manifest. That comparison checks integrity against the manifest in hand; it does not establish who created the file or whether the statement in it is accurate. Keep the manifest under the receiving organization's established access and provenance controls.

A trimmed clip, a redacted still and a screen recording are useful attachments if their roles are clear. Give each derived file its own identifier and link it to its source. Record the edit or export step and the relationship between clip offsets and the original timeline when that relationship is available. Use the original for provenance review and the derivative for the purpose for which it was made. If a source file cannot be transferred under the applicable handling rules, declare it withheld and record the authorized retrieval path rather than silently treating a derivative as complete evidence.

Ask whether the offered UI04 package permits a reviewer to retrieve the required files without the original operator's device, login or live connection. If a proprietary player is necessary, document the exact version, installation requirements and what the player exposes. Determine whether the organization accepts that dependency before accepting the workflow. A screenshot of a menu item is a prompt to request a sample, not a successful export test.

Design corrections and retransmissions into the package

Use a package identifier and revision to make retransmission recognizable. On receipt, compare the identifier, revision and manifest digest. A repeated revision with the same digest is the same package and can be acknowledged without creating a second observation. If the identifier and revision match but the digest differs, flag a conflict. Keep both receipts until someone can determine what changed. An intended correction should have a new revision, a reason and a reference to the previous one.

Separate an acknowledgement of arrival from a decision about completeness. A receiving team may be able to open the package even though the original clip is missing. One useful receipt records arrival, identity verification, the count of expected and verified files, unresolved fields and the person or role that reviewed it. If a required attachment arrives later, record what changed and link the follow-up receipt. An archive that simply replaces the first upload makes it difficult to reconstruct what the second team actually knew at the time.

Test a transfer that stops halfway through. A manifest may arrive before a large video; the receiver should retain a readable partial status rather than reject the existence of the observation or imply that all evidence is present. Agree which incomplete states are allowed for a provisional review and which make the final replay unacceptable. A second test should restore the missing file under the same identity and verify that no duplicate observation appears.

Run the replay without the original operator present

Prepare a small fixture with a known answer sheet and give the package to someone who did not assemble it. Include a source file, a derived viewing copy, two distinct position roles and two events with overlapping time intervals. Provide one duplicate transfer and one correction. Withhold an attachment in a separate test case. The reviewer should find the specified frame, explain the position labels, state the limits of timing and distinguish the correction from a new observation. Ask the reviewer to log any point at which they had to guess or ask for an undocumented convention.

Use observable acceptance results. For each required file, record whether it was present, readable and matched the manifest. For each required field, record whether it was present with the correct meaning, present with an explicit limitation, missing or contradictory. For each replay task, record whether the reviewer reached the expected answer from the package alone. A single aggregate score can hide a critical missing field, so keep individual failures and assign owners. Retest the changed interface and the related failure case after a correction.

Keep the synthetic test files and the received supplier sample separate. A successful fixture verifies that your record design and reviewing process can represent the expected cases. A successful supplier sample verifies only the observed behavior of the equipment and software versions identified with that sample. Preserve both results, including settings that affect exports and any known gaps. Repeat the relevant tests when a camera, controller, firmware or export tool changes.

Ask for the files before accepting the workflow

For a UI04 configuration discussion, bring a short statement of what your receiving team must reconstruct. Request the quoted hardware and software identifiers, a representative original recording, any corresponding controller capture and flight-data sample, and the documentation that defines each timestamp and position field. Ask the supplier to indicate which items are standard, optional or unavailable for the quoted configuration. If your team only requires a screen recording, say so; if it requires an original sensor file and a documented time relationship, place that explicitly in the acceptance request.

The deciding artifact is a handoff another reviewer can replay without relying on memory or a live demonstration. It should show the original observation, the path from source to derivative, the meaning of any time and position values, and the unresolved information. That record gives a procurement team a concrete basis for accepting the proposed export, requesting a better sample or limiting the intended use.
